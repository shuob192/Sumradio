# Sumradio 要件定義書

**無線交信を文字で残し、クラウドAIで状況と要求を整理して、人間が確認できる対応事項にする。**

本書は開発開始前の計画です。音声の取り込みから文字起こし、情報整理、確認までを、一つのアプリで操作する構成を目指します。

## 1. 解決したい課題

災害発生時、対策本部などでは、現場から届く無線を聞きながら、場所、人数、状況、要請内容を記録します。交信が続くと、聞き漏らしの確認や、複数の場所で発生した要求と対応状況の照合が難しくなります。

Sumradioは、交信をそのまま確認できる文字記録と、AIが整理した対応ボードを一画面にまとめます。想定利用者は、本部で交信を受け、現場への対応を調整する記録担当者です。当日のデモでは、架空の状況を伝える訓練交信を使います。

## 2. 利用の流れ

音声入力はすべてマイク経由とし、無線機の受信音声や訓練の読み上げをマイクで取り込みます。録音はWAV形式で保存し、PC内のWhisperで文字起こしします。結果はMarkdown形式の交信記録として保存し、画面へ表示します。その文字記録をクラウドのLLMへ渡して状況と要求を整理し、JSON形式のタスク候補として対応ボードへ追加します。

**文字起こしは、タスク整理の完了を待たずに表示します。** 利用者は交信を先に読み、後から届く候補と照合できます。録音・文字記録・対応事項の関係を保ち、必要なときに元の交信へ戻れるようにします。

## 3. 交信から整理する情報

| 項目 | 確認したいこと |
| --- | --- |
| 発信者 | 誰が報告しているか |
| 宛先 | 誰に伝えているか |
| 場所 | どこで起きていることか |
| 要救護者の状況 | どのような状態と報告されているか |
| 要救護者の人数 | 合計と内訳は何人か |
| 要求 | 何を、どれだけ、どのように対応してほしいか |

発信者と宛先は「本部、本部、こちら調査一班」のような発話から読み取ります。要救護者の人数と物資の数量を分けます。明示的な要求がなくても、人命・安全・避難所運営・物資など、本部による確認や対応要否の判断が必要な状況報告は「状況確認」のタスク候補として抽出します。現場からの「要請」と、報告内容から生成した「状況確認」を区別し、発話にない具体的な対応内容や優先順位は補いません。対応判断を必要としない情報共有はタスク候補0件を許容し、不明な箇所は「未確認」として残します。

LLMによるタスク抽出時は、[和文通話表](japanese_phonetic.md)と[欧文通話表（NATO）](nato_phonetic.md)を文字起こしの解釈を助ける資料として渡します。機械的な置換は行わず、LLMが文脈から通話表の使用を判断します。解釈した文字は表の「文字」欄に合わせ、「朝日のあ」は「ア」、「アルファ」は「A」と記録してタスクへ反映します。「ホテルへ向かって」のような通常の語句は文字コードへ置き換えず、判断が曖昧な場合は「未確認」とします。文字起こし原文を保持し、通話表を音声認識モデルの補助文には使用しません。

## 4. 当日作る機能

| 機能 | 利用者ができること |
| --- | --- |
| 音声の取り込み | 無線機の受信音声や訓練の読み上げをマイクで入力する |
| 文字起こしの表示 | 発話中の字幕と、発話後の時刻付き交信記録を確認する |
| AIによる整理 | 発信者・宛先・場所・状況・人数・要求を整理し、「要請」または「状況確認」のタスク候補を受け取る |
| 内容の確認と訂正 | 原音と文字記録を比較し、元の認識結果を残して訂正する |
| 対応ボード | 3つのボードで管理し、種別を表示した候補を人間が承認・編集・破棄・状態変更する |
| 根拠と履歴の確認 | 対応事項から元の交信へ戻り、訂正や状態変更、再起動後の記録を確認する |

画面は、ライブ字幕、交信の一覧、対応ボードを中心に構成します。「文字起こし中」「AI整理中」「整理失敗」と人間による確認状態を分け、現在どこまで処理できたかを示します。

## 5. 人間が確認する範囲

文字起こしとLLMの整理結果は、どちらも確認前の情報として表示します。要救護者の状態の診断や救護の優先順位の決定は行わず、報告された内容を記録・整理します。宛先と対応担当を混同せず、担当の割り当ても人間が確認します。

「未完了」「保留」「到着は未確認」を完了として扱わないことを重視します。完了報告や同じ要求と思われる交信は、関連するタスクと根拠を示す候補にとどめます。タスクの統合・承認・対応済みへの変更は、人間の操作で確定します。

### タスクの状態遷移

AIが文字起こしから抽出した内容は、種別にかかわらず「タスク候補」ボードへ追加し、カードに「要請」または「状況確認」を表示します。新しいボードは追加せず、「タスク候補」「未対応」「対応済み」の3つで管理します。

人間が対応対象として承認した候補は「未対応」へ移動し、不要な候補は破棄します。「状況確認」は、本部担当者が報告内容を確認して対応要否を判断した後、手動で「対応済み」へ移動します。すべての状態変更には人間の明示的な操作を必要とし、AIが自動で状態を確定することはありません。

## 6. 利用条件とデモの完成目標

音声の文字起こしはPC内で行い、クラウドには文字起こしと整理に必要な関連情報を送ります。音声WAVはPC内に保存します。タスクの自動整理にはインターネット接続が必要です。通信が途切れた場合も録音と文字記録を続け、整理待ちを表示し、手動で対応事項を登録できるようにします。

デモでは、クラウドでの文字処理を含めて同意を得た訓練音声を使います。[無線交信台本](無線交信台本.md)の全10交信を検証用とし、90秒デモには01・02・03を使用します。読み合わせで時間が足りない場合は01・02の2交信に絞ります。青葉避難所の飲料水、若葉公園の救急隊派遣・搬送調整、03を使う場合は青葉北線の現地確認・土砂撤去を区別し、人間が候補を確認して「未対応」へ登録します。台本には完了報告がないため、デモのタスクは「未対応」のまま残します。完了操作は、デモとは別の操作検証で確認します。

会場で使う1台のPCを操作の拠点とし、ローカルの文字起こしとクラウドの情報整理をつないで動かすことを当日の完成目標とします。
