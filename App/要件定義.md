# Sumradio 要件定義書

**無線交信を文字で残し、クラウドAIで状況と要求を整理して、人間が確認できる対応事項にする。**

本書はSumradioの製品要件です。音声の取り込みから文字起こし、情報整理、確認までを、一つのアプリで操作します。実装・検証の現在の状況はREADMEと検証記録を参照してください。

### デモ構成の追加（2026-09-15）

架空の青葉地区10交信に加え、[東京都内の実在地名3交信](無線交信台本_実在地名.md)を使用します。画面でデモを選び、実施回ごとに交信・タスク・履歴を保存して再開できます。実在地名のデモも被害・人数・要請は架空の訓練設定です。

両デモでは事前登録された位置マスターと同じデモ内で人間が確認した位置だけを使用し、地名の外部検索は行いません。未登録地名は「場所未確認」として手動指定します。公園・橋の代表点と詳細地点を区別します。録音停止中にデモを切り替えられ、以前の実施回で進行中の抽出結果は元の実施回に保存します。通常利用での設定済み地名検索は後述の要件に従います。

開始画面で実在デモ・通常利用の対象地域を都道府県と市区町村（任意）で指定できます。地域は実施回ごとに保存し、場所の候補をその地域に絞ります。地域指定なしも許可し、架空デモは青葉地区固定です。地域外または交信と矛盾する場所は未確認とし、交信・タスクを消さず人間の確認に回します。地域設定を交信原文や音声認識の補助文へ埋め込みません。

## 1. 解決したい課題

災害発生時、対策本部などでは、現場から届く無線を聞きながら、場所、人数、状況、要請内容を記録します。交信が続くと、聞き漏らしの確認や、複数の場所で発生した要求と対応状況の照合が難しくなります。

Sumradioは、交信をそのまま確認できる文字記録と、AIが整理した対応ボードを一画面にまとめます。想定利用者は、本部で交信を受け、現場への対応を調整する記録担当者です。当日のデモでは、架空の状況を伝える訓練交信を使います。

## 2. 利用の流れ

音声入力はすべてマイク経由とし、無線機の受信音声や訓練の読み上げをマイクで取り込みます。録音はWAV形式で保存し、PC内のWhisperで文字起こしします。結果はMarkdown形式の交信記録として保存し、画面へ表示します。その文字記録をクラウドのLLMへ渡して状況と要求を整理し、JSON形式のタスク候補として対応ボードへ追加します。

**文字起こしは、タスク整理の完了を待たずに表示します。** 利用者は交信を先に読み、後から届く候補と照合できます。録音・文字記録・対応事項の関係を保ち、必要なときに元の交信へ戻れるようにします。

## 3. 交信から整理する情報

| 項目 | 確認したいこと |
| --- | --- |
| 発信者 | 誰が報告しているか |
| 宛先 | 誰に伝えているか |
| 場所 | どこで起きていることか |
| 地図表示 | 場所を地図上のどの地点へ対応させ、どの記号で示すか |
| 要救護者の状況 | どのような状態と報告されているか |
| 要救護者の人数 | 合計と内訳は何人か |
| 要求 | 何を、どれだけ、どのように対応してほしいか |

発信者と宛先は「本部、本部、こちら調査一班」のような発話から読み取ります。要救護者の人数と物資の数量を分けます。明示的な要求がなくても、人命・安全・避難所運営・物資など、本部による確認や対応要否の判断が必要な状況報告は「状況確認」のタスク候補として抽出します。現場からの「要請」と、報告内容から生成した「状況確認」を区別し、発話にない具体的な対応内容や優先順位は補いません。対応判断を必要としない情報共有はタスク候補0件を許容し、不明な箇所は「未確認」として残します。

LLMによるタスク抽出時は、[和文通話表](japanese_phonetic.md)と[欧文通話表（NATO）](nato_phonetic.md)を文字起こしの解釈を助ける資料として渡します。機械的な置換は行わず、LLMが文脈から通話表の使用を判断します。解釈した文字は表の「文字」欄に合わせ、「朝日のあ」は「ア」、「アルファ」は「A」と記録してタスクへ反映します。「ホテルへ向かって」のような通常の語句は文字コードへ置き換えず、判断が曖昧な場合は「未確認」とします。文字起こし原文を保持し、通話表を音声認識モデルの補助文には使用しません。

## 4. 当日作る機能

| 機能 | 利用者ができること |
| --- | --- |
| 音声の取り込み | 無線機の受信音声や訓練の読み上げをマイクで入力する |
| 文字起こしの表示 | 発話中の字幕と、発話後の時刻付き交信記録を確認する |
| AIによる整理 | 発信者・宛先・場所・状況・人数・要求を整理し、「要請」または「状況確認」のタスク候補を受け取る |
| 内容の確認と訂正 | 原音と文字記録を比較し、元の認識結果を残して訂正する |
| 対応ボード | 3つのボードで管理し、種別を表示した候補を人間が承認・編集・破棄・状態変更する |
| 対応マップ | タスク候補と未対応タスクの場所をOpenStreetMap上で確認し、記号から状況や要請の種類を把握する |
| 根拠と履歴の確認 | 対応事項から元の交信へ戻り、訂正や状態変更、再起動後の記録を確認する |

画面は、ライブ字幕、交信の一覧、対応ボード、対応マップを中心に構成します。「文字起こし中」「AI整理中」「整理失敗」と人間による確認状態を分け、現在どこまで処理できたかを示します。

### 対応マップ

LLMは文字起こしから、地名・施設名・道路や橋などの地点表現と、地図表示に使う状況・要請の分類を抽出します。座標そのものは推測せず、アプリが位置マスターまたはOpenStreetMapを利用する地名検索によって候補を取得します。候補が複数ある場合や場所を特定できない場合は人間に確認を求め、確定前の地点を確定済みとして表示しません。

「タスク候補」と「未対応」のカードは地図へ表示します。「青葉橋が崩落している」のような状況確認には通行障害を示すバツ印、「青葉避難所へ飲料水を手配してほしい」のような要請には水滴印を表示します。負傷者は血のしずく（🩸）、救助・搬送は救急車（🚑）で区別し、負傷者の搬送は両方表示できます。体調不良・医療、火災・煙、浸水、建物被害、通信障害、行方不明・安否確認、トイレ・衛生、物資、避難、停電、その他も決められた記号へ分類し、凡例と文字ラベルを併記します。血のマークは出血の有無・出血量を示さず、記号と並び順から救護の優先順位や危険度をAIが決めるものではありません。人間は場所と記号を訂正できます。

候補段階のピンは未確認と分かる表示にし、人間が承認して「未対応」へ移すと未対応の表示へ切り替えます。同じ地点に複数のタスクがある場合は個別に確認できるようにし、一つのピンで上書きしません。ピンを選ぶとカード、元の交信、根拠を確認できます。人間がタスクを「対応済み」へ移した場合、または候補を破棄した場合は、該当するピンを通常の地図から消します。タスク、確定した場所、記号、状態変更の履歴は削除せず保存します。

## 5. 人間が確認する範囲

音声認識に誤りがあっても、読み取れる要請を一律に破棄しません。品目などに不確かさがある場合は確認を要する候補として提示し、原文・意味の仮説・人間による訂正を区別します。誤認識の仮説によって数量や地名などを自動確定しません。

地名の解釈候補が対象地域の登録地点1件に一致し、対象タスクと根拠の対応が明確な場合は、人間が「承認・地図表示」を1回押して地名の解釈と位置を確認できます。代表点か詳細地点かを操作前に表示し、原文・数量・タスク状態は変更せず、確認者・時刻・採用解釈・根拠を保存します。未登録・同名複数・地域外・不明な入口や曖昧なタスク対応では手動指定を残します。

文字起こしとLLMの整理結果は、どちらも確認前の情報として表示します。要救護者の状態の診断や救護の優先順位の決定は行わず、報告された内容を記録・整理します。宛先と対応担当を混同せず、担当の割り当ても人間が確認します。

「未完了」「保留」「到着は未確認」を完了として扱わないことを重視します。同じ要求と思われる交信から候補が作られた場合は、重複の可能性と関連するタスク・根拠を示します。人間が不要な候補を破棄し、必要に応じて既存タスクの内容や根拠を編集します。初期版に専用のタスク統合機能は設けず、数量の自動合算や既存タスクの自動変更は行いません。

完了報告は、関連する既存タスクの確認事項として表示します。完了報告だけで新規タスクを作る必要はなく、新しい対応が必要な場合に限って候補を追加します。既存タスクを「対応済み」にする操作は人間が行います。

### タスクの状態遷移

AIが文字起こしから抽出した新規タスク候補は、種別にかかわらず「タスク候補」ボードへ追加し、カードに「要請」または「状況確認」を表示します。手動登録でも人間が種別を選び、同じく「タスク候補」から開始します。新しいボードは追加せず、「タスク候補」「未対応」「対応済み」の3つで管理します。

人間が対応対象として承認した候補は「未対応」へ移動し、不要な候補は破棄します。「要請」は対応完了後、「状況確認」は本部担当者が報告内容を確認して対応要否を判断した後、手動で「対応済み」へ移動します。登録後の状態変更には人間の明示的な操作を必要とし、AIが自動で状態を確定することはありません。

地図のピン表示はタスクの保存状態から自動更新しますが、これはボード状態の自動変更ではありません。場所候補の確定・訂正とタスクの状態変更は人間が行い、地図からAIがタスクを自動承認・完了することはありません。

## 6. 利用条件とデモの完成目標

音声の文字起こしはPC内で行い、クラウドには文字起こしと整理に必要な関連情報を送ります。音声WAVはPC内に保存します。タスクの自動整理、未取得の地図表示、OpenStreetMapを利用する地名検索にはインターネット接続が必要です。通信が途切れた場合も録音、文字記録、ボード操作を続け、保存済みの場所と取得済み地図があれば表示を維持します。未処理の交信は「整理待ち」、実行に失敗した交信は「整理失敗」、場所を確定できないタスクは「場所未確認」と区別し、手動で対応事項と場所を登録できるようにします。

デモでは、クラウドでの文字処理を含めて同意を得た訓練音声を使います。[無線交信台本](無線交信台本.md)の全10交信を検証用とし、90秒デモには01・02・03を使用します。読み合わせで時間が足りない場合は01・02の2交信に絞ります。青葉避難所の飲料水、若葉公園の救急隊派遣・搬送調整、03を使う場合は青葉北線の現地確認・土砂撤去を区別し、人間が候補を確認して「未対応」へ登録します。架空の地名はデモ用の位置マスターへ座標を登録し、青葉避難所には水滴印、青葉北線には通行障害の印が表示されることを確認します。台本には完了報告がないため、デモのタスクは「未対応」のまま残します。ピンが消える動作を含む完了操作は、デモとは別の操作検証で確認します。

会場で使う1台のPCを操作の拠点とし、ローカルの文字起こしとクラウドの情報整理をつないで動かすことを当日の完成目標とします。
